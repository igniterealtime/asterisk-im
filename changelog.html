Asterisk-IM Plugin Changelog

3.0.0 -- unreleased

  • [#18] - Now requires Openfire 5.0.0 or later, and Java 17 or later
  • Built against the Openfire 5 plugin parent (Jetty 12 / Jakarta EE8 JSP compilation)
  • Upgraded the Asterisk-Java library to 3.42.2, which supports Asterisk 10 through 23
  • Verified against every Asterisk major version from 16 through 23 over AMI
  • [#17] - Corrected the database schema scripts to use Openfire's ofVersion table, which replaced jiveVersion in Openfire 3.7
  • Fixed PJSIP device discovery: devices are now reported as PJSIP/<endpoint> rather than the bare AOR name, so that they match live channel names and can be dialled. Mappings stored by 2.0.0 keep the old value and have to be re-selected under Phone Mappings; see the readme
  • The plugin no longer bundles its own SLF4J/Log4j jars, which detached its log output from Openfire's logging configuration
  • Upgraded Smack to 4.4.8 in the client library
  • Creating or editing a phone server while the plugin is disabled now reports the problem instead of failing with a NullPointerException
  • Corrected the Smack 3 era client API example in this plugin's readme
  • [#29] - Editing a phone server now reconnects with the edited details. Previously the change reached the database while the connection built from the old details stayed in use, so it had no effect until Openfire restarted, and details that did not work went unreported
  • [#29] - A phone server that cannot be connected to now says why on the settings page, rather than only writing the reason to the log
  • [#29] - The Asterisk context is checked against the dialplan when it is saved. A context that does not exist made every call fail with nothing to say why
  • [#29] - Telephony is no longer offered to a client that cannot use it. The phone feature was advertised over service discovery to any user with a phone mapping, whether or not they had a primary phone and whether or not the phone server was connected, so clients presented a dial pad for calls that could not be placed
  • [#29] - Dialling as a user who has no phone mapping, or no primary phone, now returns an error to the client instead of throwing a NullPointerException that left the request unanswered
  • The readme has gained an "Upgrading from 2.0.0" section, covering the Openfire 5 and Java 17 requirement, the phone mappings that have to be re-selected, and confirmation that the database needs nothing done to it
